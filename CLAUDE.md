# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Screensy is a peer-to-peer (WebRTC) screen sharing app. The video stream goes directly from the broadcaster's browser to each viewer's browser. The server side only does signaling and serves static files.

The repository is a pnpm workspace with four packages, plus deployment config at the root:

- `screensy-protocol/`: the signaling protocol as Zod schemas (`protocol.ts`), shared by the server and the client. Both parse every message they receive with them. Node and esbuild read the TypeScript source directly (its `exports` point to `protocol.ts`).
- `screensy-rendezvous/`: the signaling server. `rooms.ts` has the rooms, the heartbeat and the configuration without a runtime (no `ws`, `node:*` or `process`): it talks to sockets through `ClientSocket` (`send`, `close`, `drop`) and gets their events through `ConnectionHandlers` (`message`, `closed`). `server.ts` runs it on Node with the `ws` library (port 4000). Node runs both directly with type stripping, so they are never compiled.
- `screensy-website/`: Static file server written in Go (port 8080). It also serves the browser client. The client is React and Mantine in `src/` (entry `src/main.tsx`); `build.mjs` bundles it, the protocol, Zod, React and Mantine with esbuild into one minified classic script, `screensy.js` (with `screensy.js.map`), and their CSS (Mantine's and the CSS Modules) into `screensy.css`, next to the sources.
- `screensy-cloudflare/`: screensy on Cloudflare Workers. `worker.ts` routes WebSocket upgrades to one Durable Object (`Rendezvous`, `getByName("rendezvous")`, for every room) that runs `RoomServer` of `rooms.ts`, and serves `/` and `/index.html` in the language of `Accept-Language` (`language.ts`, like `main.go`). Static Assets serve every other path without the Worker (`run_worker_first`). `build.mjs` copies the built website into `public/`. Wrangler bundles the Worker, so it imports `screensy-rendezvous/rooms` directly.
- Root: `docker-compose.yaml` (rendezvous, website, Caddy reverse proxy), `Caddyfile` (the template for a domain). `docker-compose.tailscale.yaml` and `Caddyfile.tailscale` are the variant for `tailscale serve`/`funnel`: Caddy serves plain HTTP on `127.0.0.1:80` only. `COMPOSE_FILE` in `.env` selects it, so that every `docker compose` command uses it.

The toolchain versions are pinned in `mise.toml`: Node, pnpm, Go and prek.

## Commands

```sh
mise install && pnpm install          # set up the toolchain and dependencies
pnpm check                            # Biome format + lint with fixes (TS, JSON, CSS, Markdown, YAML; HTML is lint-only)
pnpm lint                             # Biome without writing changes
pnpm typecheck                        # tsc (no emit) in every package
pnpm --filter screensy-website build  # bundle src/ -> screensy.js and screensy.css with esbuild
pnpm test:protocol                    # protocol checks against the rendezvous server (port 4000)
pnpm test:protocol:cloudflare         # the same checks against the Durable Object in wrangler dev (port 8787)
pnpm test:e2e                         # browser checks in headless Chrome (needs Go and Chrome; ports 4000, 8080, 8090, 8787, 9333)

pnpm --filter screensy-rendezvous start            # ws://localhost:4000
cd screensy-website && go run .                    # http://localhost:8080 (must run from screensy-website/, it serves ".")
cd screensy-website && go vet ./... && gofmt -l .  # Go checks
pnpm --filter screensy-cloudflare dev              # the Worker in wrangler dev, http://localhost:8787
pnpm --filter screensy-cloudflare run cf:deploy    # deploy to Cloudflare (after wrangler login); "deploy" would run pnpm's own deploy

docker compose build    # the build context is the repo root (the lockfile lives there)
docker compose up -d
```

`--filter` matches the `name` in each package's `package.json`, not the directory name. WebRTC requires HTTPS outside `localhost`, so test a real deployment behind Caddy.

### Tests

The two scripts in `tests/` are plain Node ESM with no dependencies of their own. They start what they need and stop it when they finish. They are not run by the git hooks; run them after changing the protocol, the client or the translations. The deploy workflow runs the protocol checks, but not the e2e test.

- `tests/protocol.mjs` starts `server.ts` with short timers (`SCREENSY_*_MS`) and checks the protocol with WebSocket clients: joining, takeover, the grace periods, resuming, socket replacement, signal and mesh signal relay validation (also for call streams), the call messages and the limit of cameras, the room instance ID, the heartbeat and room deletion. With `SERVER=cloudflare` (`pnpm test:protocol:cloudflare`), it runs the same checks against `wrangler dev` with the timers as `--var`, except the two about the Node entry point (`nodeOnly`). It borrows `ws` from `screensy-rendezvous`, because it needs `terminate()` and the `Host` header. Its clients answer `ping` like the browser client, unless `answerPings: false`.
- `tests/e2e.mjs` builds and starts the website, the rendezvous server and a proxy on port 8090 that routes like the Caddyfile, then drives headless Chrome over CDP. The pages name the elements that the checks use with `data-testid`, which stays the same in every language and inside the portals of Mantine (the menu drawer, the dialog, the notifications); state shows in `data-*` attributes (`data-kind`, `data-self`, `data-status`, `data-speaking`). The init script adds `$t(id)` and `$t(id)` to find them, `Page.type` sets an input as typing would (React listens to `input`, `change` and `focusout`, not to a plain `value`), and `Page.openMenu` and `closeMenu` open the drawer, whose content only exists while it is open. `getDisplayMedia` returns a canvas stream, because headless Chrome cannot accept the screen picker. Chrome keeps its default mDNS host candidates: turning them off hid a real connection bug once. The proxy can break a page's WebSocket without a close frame, for pages that set the cookie `e2e=<tag>`. The init script records every `RTCPeerConnection` (`__pcs`) and every `replaceTrack` call (`__replaced`), and `__replaceHook` can delay or fail `replaceTrack` for a test. `__nextCapture` sets the size, color and audio of the next fake capture. `__chatDropLive` drops that many live chat sends on the data channels (one per peer), to check that a lost message is asked for again. Chrome runs with its fake microphone and permission prompt (`--use-fake-device-for-media-stream`, `--use-fake-ui-for-media-stream`), because an oscillator in an `AudioContext` stops on a machine without audio output; the init script records the microphones and cameras (`__microphones`, `__cameras`, `__userMediaCalls`), and `__denyMicrophone` and `__denyCamera` refuse them. The last section starts `wrangler dev` (as a process group, because it runs workerd as a child) and checks that the Worker picks the same language as the Go server, that Static Assets serve the built files, and that a viewer gets a presentation, a chat message and the call through the Durable Object; the e2e server allows two cameras from the section with several presenters on, so that the call checks the limit; `SKIP_CLOUDFLARE=1` skips it. `CHROME` sets the Chrome binary, `SHOTS=<dir>` saves screenshots and `DEBUG=1` prints the server output.

## Tooling conventions

- Biome config follows `~/Workspace/templates` (`assets/biome/default.json`): 2-space indent, line width 120.
  - `screensy-website/biome.json` is a nested config (`"extends": "//"`) with the overrides of the Mantine template (`~/Workspace/mantine-template`): `noImplicitBoolean`, `noReactSpecificProps` and `noUndeclaredDependencies` are off. Biome turns on its React rules (hooks, JSX) by itself, because the package depends on React.
  - Functions are arrow functions assigned to `const`, never `function` declarations or expressions: `useConsistentFunctionStyle` (`style: "expression"`) and `useArrowFunction` are errors. Class methods stay methods. Arrow functions are not hoisted, so define them before the top-level code that calls them (for example `numberFromEnv` in `rooms.ts`). Where a function needs a dynamic `this` (the prototype patches in the e2e init script), use the method syntax of an object literal.
  - Fix lint violations in code instead of disabling rules.
- TypeScript 7 (native compiler), only for type checking. The rendezvous and protocol tsconfigs set `erasableSyntaxOnly` and `verbatimModuleSyntax`, which Node's type stripping requires. Do not use enums, namespaces or parameter properties there, and use `import type` for type-only imports.
- The website tsconfig uses `moduleResolution: "bundler"`, `allowImportingTsExtensions` (relative imports name the `.ts` or `.tsx` file), `jsx: "react-jsx"`, and the stricter checks of the Mantine template (`noUnusedLocals`, `noUnusedParameters`, `erasableSyntaxOnly`, `noFallthroughCasesInSwitch`). esbuild emits an IIFE, because the HTML loads `screensy.js` with a plain `<script>`; it builds with `NODE_ENV` "production", so that React and Mantine leave out their development checks. The CSS Modules (`*.module.css`, declared in `css-modules.d.ts`) are plain CSS without PostCSS: use Mantine's CSS variables, not the mixins of `postcss-preset-mantine`. The template's Vite and React Compiler are not used: esbuild keeps the build that Docker and Cloudflare share.
- Validation uses Zod 4 (`import * as z from "zod"`; the named import `{ z }` defeats tree shaking and pulls all of Zod, locales included, into the bundle). Messages, `localStorage` values (quality settings, blur strength, devices) and the inputs of the menu and the dialog go through schemas instead of hand-written type guards.
- Node does not strip the types of `.ts` files under `node_modules`. Workspace links resolve to the package directory, so `screensy-protocol` works in development; the rendezvous Dockerfile therefore keeps the workspace layout (`pnpm install --filter "screensy-rendezvous..."`) instead of `pnpm deploy`, which would copy the package into `node_modules`.
- prek git hooks (`prek.toml`) are installed by the `prepare` script on `pnpm install`. On commit, they run the builtin whitespace/merge-conflict/large-file checks, `biome check --write` and `gofmt`. Run them manually with `mise exec -- prek run --all-files`.
- Claude Code hooks in `.claude/`, adapted from the templates repo, need `jq`:
  - `post-edit.sh` runs `biome check --write` or `gofmt` on each edited file.
  - `stop-check.sh` blocks the stop when Biome, `pnpm -r typecheck`, `go vet` or `gofmt` report problems.

## Architecture

### Signaling protocol (`screensy-protocol/protocol.ts`)

The server and the client share the Zod schemas and the types inferred from them (`ClientMessageSchema` for the messages after `join`, `JoinSchema`, `ServerMessageSchema`). A protocol change goes into `protocol.ts`, and the type checker then shows what `rooms.ts` and the client must handle. Messages are JSON with a `type` field. There are no fixed roles: anyone in a room can present, up to `MAX_PRESENTERS` people at once (4; `SCREENSY_MAX_PRESENTERS` changes it, and the tests use 1 for the scenarios about a single presenter). The server sends the limit in `welcome` as `maxPresenters`, and the limit of cameras in the call (`MAX_CAMERAS`, 4; `SCREENSY_MAX_CAMERAS`) as `maxCameras`.

1. The client connects to the WebSocket at the same host and path as the page and sends `join` with `roomId` (the URL hash, lowercased by the client), `name` and an optional `resumeToken`. The server answers `welcome` (`selfId`, `connectionId`, `resumeToken`, `roomInstanceId`, `maxPresenters`, `maxCameras`, `iceServers`) and then sends `roomstate` to everyone. `roomInstanceId` is a random ID of the room, new whenever the room is created again (after everyone left, or after a restart of the server); the chat history of a page belongs to one.
2. `roomstate` is the whole state of the room: `participants` (`id`, `connectionId`, `name`, `connected`) and `presenters` (`participantId`, `streamId`, `hidden`, `status: "live" | "reconnecting"`, `disconnectReason: "left" | "lost" | null`, `graceRemainingMs: number | null`), and `calls` (the voice call, see 4). The server sends it after every change, and clients reconcile against it.
3. A client captures its screen first and then sends `present`. The server assigns a new `streamId` and answers `presentaccepted` (before the next `roomstate`). In a full room, `present` must name a presenter in `replace`, who loses the seat (this is how a takeover works; the start dialog lets the person choose); otherwise the server answers `presentrejected` with `reason: "full"`. Below the limit, `replace` is ignored. `present` with `resume: true` is only accepted while the sender still holds a seat; otherwise the server answers `presentrejected` with `reason: "seat-lost"`. The client that lost its seat names the presenter who is new in the latest `roomstate` as the one who took over. `stoppresenting` frees the seat. `streamstate` sets `hidden` for the sender's stream (the "Hide screen" button). The server resets `hidden` on every `present`, so a client that resumes while hidden sends it again.
4. SDP/ICE goes through `signal`. The sender sets `to`, `toConnection` and `streamId`, and the server relays it with `from` and `fromConnection` only if the recipient is connected with that `connectionId`, the stream is active, and the sender or the recipient owns that stream: its presenter, or the participant in the call who sends it. `kind` is `offer | answer | candidate`. WebRTC connections are keyed by `(participantId, connectionId)`, so a new `connectionId` means "rebuild the connections". `meshsignal` carries the same payloads for the mesh (the connections without media for the chat), without a `streamId`: the server relays it between any two participants, if the recipient is another participant connected with that `connectionId`.
   The call: `joincall` (with `muted` and `camera`) puts the sender in `roomstate.calls` (`participantId`, `streamId`, `muted`, `camera`, in the order of joining) with a new `streamId` from the same counter as the presentations, also when the sender is in the call already; `leavecall` takes it out, and `callstate` changes `muted` and `camera`. A camera is only turned on below `maxCameras` cameras in the room; otherwise it stays off and the sender gets `camerarejected`. The cameras need no seat: unlike a screen, a page can open its camera again without a click. Being in the call belongs to the connection: a closed or replaced socket leaves the call, also for a presenter who keeps the seat for the grace period, and the page that comes back joins again. There is no limit on the number of participants in the call.
5. Reconnection: the resume token lives in `sessionStorage` (`screensy.resume.<roomId>`). A presenter whose socket closes keeps the seat as `reconnecting`; other participants are removed at once. The grace period depends on the close code: a clean close (1000, 1001, 1005: a reload or a closed tab, which look the same) gives `disconnectReason: "left"` and `LEFT_GRACE_MS` (30 s), anything else (1006 for a broken connection) and a missed ping give `"lost"` and `LOST_GRACE_MS` (5 min). `graceRemainingMs` is the time left, sent as a duration so that the clocks need not agree. A `join` with a known token takes over that participant, even if its old socket is still open: the old socket gets `replaced` and is closed, and its late `close` event is ignored. Rejoining stops the grace timer (`graceRemainingMs: null`): the seat then stays until the participant resumes or frees it, or someone takes over. A room is deleted when it has no participants left, including those in the grace period.

The heartbeat is a pair of messages, the same on Node and on Workers (a Worker cannot send ping frames or terminate a socket): every 15 s, the server sends `ping` to every connection, also before `join`, and drops (`ClientSocket.drop`) those that sent nothing since the previous one; it counts as `"lost"` at once, without waiting for a close code. The browser answers `pong` in `SignalingConnection` and never passes `ping` on. The server sends it, because browsers delay the timers of background tabs, but not the messages they receive. The timer only runs while there are connections, so that an idle Durable Object can be evicted. `SCREENSY_LEFT_GRACE_MS`, `SCREENSY_LOST_GRACE_MS` and `SCREENSY_PING_INTERVAL_MS` shorten the timers for testing. Incoming messages are parsed with the schemas (`safeParse`); the server silently drops invalid ones, the client drops them with a console warning. The schemas also check the WebRTC payload of a `signal` (`sdp` a string; the candidate fields, of which `sdpMid`, `sdpMLineIndex` and `usernameFragment` may be null, as `RTCIceCandidate.toJSON()` sends them).

### Browser client (`screensy-website/src/`)

The logic has no UI: `room-controller.ts`, `call-controller.ts`, `tile-views.ts` (the `TileView`s from the room state, as pure functions), `signaling.ts`, `outgoing-stream.ts`, `outgoing-peers.ts`, `outgoing-call.ts`, `devices.ts`, `incoming-stream.ts`, `peer-link.ts`, `peer-mesh.ts`, `chat.ts`, `chat-protocol.ts`, `file-transfer.ts`, `capture.ts`, `blur.ts`, `quality.ts`, `stats.ts`, `storage.ts`, `format.ts` and `room-name.ts`. The UI is React with Mantine in `components/`, and Jotai in between:

- `state/atoms.ts` has one Jotai store (`createStore()`) and its atoms, and `state/views.ts` the types of what they hold (`StageView`, `ToolbarView`, `DialogView`, `ChatView`, `CallView`, `DevicesView`, …). The controllers live outside React: `RoomController.render()` and `CallController.show()` build the views and `store.set` the atoms, and the components read them with `useAtomValue` under `<Provider store>`.
- The components call the controllers for what the person does, through `ControllerContext` (`useController()`): `openStartDialog`, `confirmDialog`, `switchScreen`, `setHidden`, `setBlurred`, `sendChat`, `attachFile`, `call.join`, `call.setCamera`, `call.changeDevice`, `setMenuOpen`, and so on. `confirmDialog`, `switchScreen`, `call.join` and `call.setCamera` call `getDisplayMedia` or `getUserMedia` first, so the components call them straight from their click and submit handlers, while the click still counts as a user activation.
- The notices are Mantine notifications (`notices.tsx`, `showNotice(id, name)`), which the controllers show directly; the same notice again replaces the shown one, and each closes after 10 s.
- What only the UI knows stays in React state: the enlarged tile, the sound setting of each tile, the sound that the browser refused before the first click, the open chat and its unread count (live messages since it was last open, from `ChatView.liveCount`), and the open menu.
- `components/`: `App` (`MantineProvider` with the dark color scheme forced, the notifications, the Jotai provider, and `AppShell`: the toolbar in the header, the stage in the main area, the chat in the aside), `Toolbar` (Tabler icon buttons with tooltips and `aria-label`; "Present", "Stop presenting" and "Join call" also have text), `Stage` (the tiles, the page-wide status, and under the stage the participants in the call without a tile), `ChatPanel`, `MenuDrawer` (a `Drawer` whose content only exists while it is open), `PresentDialog` (a `Modal`), `EchoChoice`, `CallAudio` and `Unsupported` (what the browser lacks, or a server that the page never reached, instead of the room). `media.ts` has the hook that plays a stream in a media element (source, sound, speaker, playing again when React moves it, and the refusal of sound before a click). Names and texts from other people are always React text, never HTML.

`main()` keeps a file dropped outside the chat from opening in place of the room (`ignoreDroppedFiles` on `window`, after the chat had its turn), creates a random room name in the hash if there is none (with `history.replaceState`, so the page does not reload) and checks browser support. `RoomController` then joins the room and reconciles every `roomstate`:

- `SignalingConnection` reconnects with backoff and drops messages while disconnected. After a reconnect, `welcome` and the next `roomstate` resynchronize everything.
- `OutgoingStream` is this client's presentation: one `RTCPeerConnection` per recipient. It has no `streamId` while awaiting `presentaccepted`. Losing the own entry in `presenters` means the seat was taken over.
  - Every connection has exactly one video and one audio transceiver (`sendonly`), even for a capture without audio, so that switching the screen (`replaceCapture`) and hiding it (`setHidden`) never renegotiate.
  - The captured tracks are sent as they are, and the preview shows the same tracks. Hiding disables them, so the viewers get black frames and silence, and the presenter's preview turns black too: both sides see the same. A switch disables the new tracks before any `replaceTrack` when hidden, and rolls every connection back to the current capture if one of them rejects the new tracks.
  - "Blur screen" (Chrome and Edge only) sends the output of a `BlurProcessor` instead of the captured video: the breakout box (`MediaStreamTrackProcessor` → `TransformStream` → `MediaStreamTrackGenerator`, declared in `breakout-box.d.ts` because `lib.dom` lacks them) halves each frame step by step (one large canvas downscale only picks some pixels, halving averages them) down to one pixel per `strength × devicePixelRatio` pixels, then scales it up to one pixel per 4 CSS pixels (`BLUR_OUTPUT_CSS_PX × devicePixelRatio`) with a `blur()` proportional to that enlargement. The strength comes from a slider in the toolbar (4–64 CSS pixels, default 24, saved in `localStorage` as `screensy.blur`), shown while blurred with its value next to it. The minimum is the size of an output pixel, below which the strength would make no difference. `setBlurStrength` changes the running `BlurProcessor` without a `replaceTrack`, and the output size does not depend on the strength, so the slider never changes the sent resolution. `devicePixelRatio` belongs to the presenter's page, so it is only a guess for the density of the shared screen (another monitor, page zoom); it is clamped at 1 or more. These streams keep running in a background tab, unlike `requestAnimationFrame` and timers. Blurring goes through the same `changeCapture` as a switch (replace on every connection, roll back on a rejection), and `Capture.preview` shows the blurred video. Hiding disables every track, including the input of the blur, so it wins over the blur.
- Quality settings (`QualitySettings`: frame rate, maximum height, maximum bitrate, degradation preference) live in `localStorage` (`screensy.quality`); `readQuality` validates each value with a Zod schema and falls back to its default (`.catch` per field; anything stored that is not an object counts as `{}`). `applyQuality` sets them on every sender with `setParameters` (`maxFramerate`, `maxBitrate`, `scaleResolutionDownBy` computed from the capture's current height, `degradationPreference`), one call at a time per connection. It runs when ICE gathering completes, when the settings change, after a switch, and when the preview `<video>` is resized (a resized shared window changes the scale factor). `getDisplayMedia` asks for the chosen frame rate, and the video track gets a matching `contentHint`.
- `StatsCollector` reads `getStats()` for the menu, only while it is open (`setMenuOpen` starts and stops a one-second timer). It keeps the previous sample per connection to turn byte and packet counters into a bitrate and a loss rate. The presenter gets one entry per viewer (`OutgoingStream.connections()`), a viewer one for the received stream (`IncomingStream.connection`). A codec is only named when packets flow, because a sender without a track still reports one.
- `IncomingStream` is one received stream per `streamId`. `PeerLink` holds back ICE candidates until the remote description is set.
- The stage shows one tile per presenter, in the order of `presenters`: a video, the name as a badge (`tile-name`: an icon for a screen or a camera, "You" for the own preview, at the own seat, and the state in the call of that participant), a status over the video (`data-status`, the per-presenter statuses), a mute button and a full-screen button. `RoomController.render()` builds a `TileView` per presenter, and React keys the tiles by participant ID, so a tile keeps its sound setting and enlargement across new streams. CSS grid lays them out evenly (`data-count`, in `Stage.module.css`); a transparent button over each tile enlarges it (`data-spotlight`). The page-wide status shows over the stage. Tiles play with sound, and fall back to muted until the first click if the browser refuses it.
- Echo: a presenter whose capture may contain this page's sound (an audio track without `restrictOwnAudio` in its settings, from a window or screen) would send the other presenters' sound back, and two of them would echo forever. `getDisplayMedia` asks for `restrictOwnAudio: true` and `selfBrowserSurface: "exclude"`, and `capturesOwnAudio()` decides when to mute the other tiles on that page (with a notice; the person can unmute one on purpose).
- Call: like a presentation, but of the microphone and the camera. `CallController` (`call-controller.ts`) is this client's part of it, in step with the room state; `RoomController` hands it the room state, the signals of the own call stream, `welcome` and `camerarejected`. `OutgoingPeers` (`outgoing-peers.ts`) is the part that both send with: one connection per recipient, offers and ICE candidates, and the sync with the room state. `OutgoingCall` sends one audio and one video transceiver (`sendonly`) to every other connected participant, in the call or not, so that everyone in the room hears and sees the call. The camera (640×360 at 24 fps, `contentHint` "motion") is asked for in the click handler of the camera button, but only sent (`replaceTrack`) once the room state shows it on, so that the room never gets more cameras than its limit; off, or after `camerarejected` (`notice-cameras-full`), the track stops, so that the camera's light goes off. The cameras are tiles on the stage after the screens (`TileView.kind` "camera", key `camera:<participantId>`, from `cameraTileViews`), always muted because the sound plays in `CallAudio`, and shown whole like the screens, never cropped; the own one is a mirrored preview. Beyond four tiles, the stage has as many columns as rows (`data-many`, `--columns`). "Join call" calls `getUserMedia` (with the echo canceller, noise suppression and automatic gain) in the click handler and sends `joincall`; muting only disables the track, which then sends silence, and tells the room with `callstate`. The stream ID comes from the own entry in `roomstate.calls`: a new one replaces the connections. After a `welcome` the page sends `joincall` again with the microphone it still has; a reload leaves the call. The received call streams are `IncomingStream`s like the presentations, played by `CallAudio` (one hidden `<audio>` per stream, with the notice `call-audio-blocked` when the browser refuses to play sound before a click). The toolbar has the join, microphone, camera and leave buttons: the microphone and the camera are toggles named as such (`aria-pressed` while they send) and filled blue while on, and only leaving is red. The badge of each tile shows its participant in the call: a microphone mark while muted, filled green while speaking. Those in the call without a tile (no camera, no screen) are badges with a phone icon in a row under the stage (`call-voice`), so that everyone who speaks shows somewhere.
  - Devices: the menu lists the microphones, cameras and speakers from `enumerateDevices()` (refreshed on `devicechange`, after a permission and when the menu opens; the browser hides the names before a permission). The choice lives in `localStorage` (`screensy.devices`, a Zod schema), as a preferred `deviceId` (`ideal`, so that a device that is gone falls back to another). Choosing a microphone or a camera during the call replaces the track on every connection (`replaceTrack`), without a new negotiation; the speaker goes to every `<audio>` of the call and `<video>` of the stage with `setSinkId`, hidden where the browser lacks it.
  - Who speaks: while someone is in the call, `CallController` reads the levels every 300 ms, as the root mean square since the previous reading from `totalAudioEnergy` and `totalSamplesDuration` in `getStats()` (`inbound-rtp` of the received audio, `media-source` of one own connection), so that a short sound between two readings counts, and marks a participant above 0.02 for 600 ms (`data-speaking` on the participant's badges, and an outline on the camera tile); a muted participant never speaks.
  - The menu's statistics also list the connections of the call, named with `stats.call`.
  - Echo with the call: the microphone's echo canceller removes the call from the speakers, but a capture that may contain this page's sound (`capturesOwnAudio`) copies the call digitally and would send it back to everyone. While someone else is in the call, such a capture's audio track is disabled before it reaches a sender, and `EchoChoice` asks: hear the call without the shared sound, or share the sound and mute the call on this page. The choice belongs to the capture (a new screen asks again); `OutgoingStream` asks `RoomController.screenAudioSuppressed` for every capture, and `refreshTrackStates` asks again on every render.
- Chat: peer to peer, so that the server carries no chat messages (on Cloudflare, each one would count as a request).
  - Files: the attach button (with a hidden file input), or files dropped on the chat (`ChatPanel` shows `chat-drop` while they are dragged over it, and leaves out folders), sends a chat message with `file` (`id`, `name`, `size`, `type`; the text may then be empty). `FileTransfers` (`file-transfer.ts`) works on the second negotiated channel of the mesh (`files`, `id: 1`), so that a large file never holds up the chat. When the channel opens, each page says its chat author IDs, the current one and those of its earlier loads (`hello`), and the IDs of the files that it can pass on (`have`, in parts of 200, and again for each new one): the files that it shared, and the files that it received whole. A receiver clicks "Download" and asks one of the peers that have the file, at random, so a file stays available while anyone who has it is here. The control messages (`hello`, `have`, `get`, `start`, `end`, `cancel`, `error`) are JSON with Zod schemas; the data are binary messages with the transfer ID in the first 4 bytes, sized to the channel's `maxMessageSize`. The sender reads the file in 1 MiB blocks and waits while more than 1 MiB is queued (`bufferedamountlow`). The receiver folds what it got into a `Blob` every 16 MiB, so that the size has no limit, and shows a "Save" link (`<a download>` on an object URL) at the end. A file without a peer that has it shows whether its sender is here ("stopped") or not ("unreachable"); a failed download can start again.
    - A reload forgets the shared `File`s: the own messages from before show "ended", with a button to choose the file again, which shares it under the same ID if its name and size are the same (otherwise the notice `file-mismatch`).
    - A received `Blob` is always `application/octet-stream`, whatever type the sender names: a Blob of `text/html` or `image/svg+xml` opened in a tab would run its scripts with this page's origin. `cleanFileName` takes the control characters, the marks and overrides of bidirectional text (which can make "exe" look like "pdf") and the path separators out of a received name, for the display and for saving.
    - Image previews (`image-preview.ts`): every held file (shared or received whole) whose first 12 bytes are a PNG, JPEG, GIF or WebP image (`sniffImageType`, never the named type) gets a second object URL, of a Blob of that type, for the preview (`ChatFileView.preview`); the download URL stays `application/octet-stream`, and SVG never previews. The receiver fetches the images of others without a click, when the named type is one of those four and the size is at most 10 MiB (`fetchesForPreview`): `FileTransfers.prefetch` queues them newest first, starts two at a time when a peer that has them is here (again on each `have`), and tries each file once, so a cancelled or failed one waits for a click. `ChatPanel` shows the preview at a fixed height, so that the log keeps following its end, and opens it larger in a `Modal` (`image-viewer`).
  - `PeerMesh` keeps one `RTCPeerConnection` without media to every other connected participant, keyed by `(participantId, connectionId)` and signaled with `meshsignal`. Of the two sides, the one whose `connectionId` is greater as a string sends the offer; the other builds its connection when the offer comes, and a new offer always replaces it. Both create the chat channel as a negotiated `RTCDataChannel` (`id: 0`). The offering side rebuilds a failed connection after 5 s, up to 3 times per `connectionId` (without TURN, a pair without a direct path never connects). `welcome` resets the mesh, like the incoming streams.
  - `Chat` keeps the history and talks to the peers over `PeerMesh`; the messages on the channel (`summary`, `request`, `messages`) are Zod schemas in `chat-protocol.ts`. A message is identified by `(authorId, seq)`: the author ID is random and new on every page load (a duplicated tab copies `sessionStorage`, so it must not carry over), and `seq` counts from 0, so a gap in the numbers shows a missing message. The order is the Lamport time, then the author and the number, the same on every page; `sentAt` is the author's clock, only for the display.
  - Sync: a page sends a `summary` (the ranges of numbers it has, per author) when a channel opens and every 20 s, and asks the peer for what it misses with `request`, from one peer at a time (a requested message is not asked for again for 5 s). A live message whose number skips ahead makes the page ask its author for the gap at once. The periodic summary also carries messages between two pages without a direct connection, through the others. A page keeps at most 1000 messages; dropping older ones raises a floor (Lamport time) under which it neither takes nor asks for messages. `messages` are split to fit the channel's `maxMessageSize`.
  - The history lives in `sessionStorage` (`screensy.chat.<roomId>`, with the `roomInstanceId` and the author IDs of the page's earlier loads, which show as the own messages), so a reload keeps it; a different `roomInstanceId` discards it. There is no signature: anyone with the link can already use any name.
  - `ChatPanel` is in the `AppShell` aside, always on the page (a closed panel is collapsed), so that the log keeps its place. The chat button shows the unread count, only for live messages from others. The panel shows how many of the other connected participants the chat reaches. Enter sends, Shift+Enter adds a line, and an Enter during an IME composition (`isComposing`, or `keyCode` 229 in Safari) does nothing.

The ICE servers come from `welcome.iceServers`, which the rendezvous server builds for every `welcome` from `SCREENSY_STUN_URLS` (default Cloudflare's public `stun:stun.cloudflare.com:3478`, on Node and on Workers; the e2e test sets it empty, so that it does not reach the internet). `{host}` is the host name that the client connected to (`hostnameOf` of the `Host` header on Node, which never throws; the request URL on Workers); URLs with `{host}` are left out when it is missing or invalid. An empty variable turns STUN off. `configFromEnv` checks the URLs against the STUN URL syntax, and the Node server exits with a message on a mistake (the Durable Object answers 500), because a browser throws on an invalid URL when it creates a connection. There is no TURN relay and no STUN server of our own: the deployments (tailnet, Funnel, Cloudflare) all use the public one, and viewers without a direct path get no video. `{host}` is for someone who runs their own STUN server on the machine: inside a tailnet, it resolves to the Tailscale address, so the browsers would get their Tailscale addresses as server-reflexive candidates and Tailscale would connect them. That STUN server must see the packets unchanged, on the host network (through port forwarding, it would see the forwarder's address; on macOS, Docker's host network does not reach the tailnet).

### Translations / i18n

`screensy-website/translations/` has the index page in each language: `en.html` and `ja.html`, small shells with `<html lang>`, the title, the description, the `<noscript>` text, `screensy.css`, `screensy.js` and `<div id="root">`. `main.go` loads them at startup and parses each filename as a BCP 47 tag (`language.MustParse`, so a bad filename panics). It serves the best match for `Accept-Language` on `/` and `/index.html`, with `en.html` as the fallback. All other paths go to `http.FileServer(".")`. The Worker picks the same way (`language.ts`).

The texts of the client are dictionaries in `src/i18n/`: `en.ts` defines the keys (`as const`), `ja.ts` has the same keys (`Messages`, so a missing one is a type error). `t(key, params)` fills in `{name}` and the like, in the language of `<html lang>` (`pageLanguage()`); React inserts the values as text. `displayName` names someone without a name a guest numbered by the order of joining (`name.anonymous`, the participant ID + 1), the same on every screen. A new language is a new dictionary and a new shell. The inputs of the menu have language-independent values (`""` for the original resolution, heights, and the `RTCDegradationPreference` values).

### Deployment notes

- `.github/workflows/deploy.yml` deploys to Cloudflare from GitHub Actions: a `check` job (`pnpm lint`, `pnpm typecheck`, `pnpm test:protocol`, `pnpm test:protocol:cloudflare`, with the toolchain from `mise.toml` by `jdx/mise-action`), then `cf:deploy` with the secrets `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID`. It runs only by hand (`workflow_dispatch`) and for tags `v*`, because a deploy ends every room. For a tag, a `release` job (the only one with `contents: write`) then runs `gh release create --generate-notes`. There is no CI for pull requests.
- Caddy routes requests that carry WebSocket `Upgrade` headers to `rendezvous:4000` and everything else to `website:8080`.
- Before deploying, set the domain on the first line of `Caddyfile`, or, with Tailscale, set `COMPOSE_FILE=docker-compose.yaml:docker-compose.tailscale.yaml` in `.env` (which then no longer loads `docker-compose.override.yaml` on its own). `.env` (from `.env.example`) is otherwise optional: it changes the STUN servers or the number of presenters. It is ignored by git and Docker.
- On Cloudflare, every room lives in the memory of one Durable Object that does not hibernate (no storage, `new_sqlite_classes` only because the free plan requires it). A deploy or a restart of the object ends every room. Only open sockets keep it in memory, not the grace timers, so it may be evicted while a lone presenter is in a grace period; untested, because local workerd does not evict. Every message from a browser counts against the free plan's 100,000 requests a day.
- `pnpm-workspace.yaml` declares the install scripts of esbuild and workerd as not needed (`allowBuilds`): they only check the platform packages, and pnpm 12 fails an install with scripts that nobody decided on.
- The website Dockerfile copies only `screensy.js` and `screensy.js.map` (which carries the sources) into the final image. esbuild runs from its platform package, so `--ignore-scripts` is fine.
- Node 25+ images do not ship corepack, so the Dockerfiles install pnpm with `npm install --global pnpm@<version>`. Keep that version in sync with `mise.toml` and `packageManager`.
